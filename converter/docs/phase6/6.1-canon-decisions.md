# Phase 6.1 — Décisions sur les items `canon-evolution-open`

Date : 2026-09-21. Base factuelle : trois jeux de données réels (WooCommerce
REST 9.x/11.1, Shopware 6.7 Admin API, Shopify Admin GraphQL 2025-xx), plus
les exports Scraper (`scraper.eloshon-export.v1`), plus ce qui est connu de
PrestaShop/BigCommerce/Wix par leurs formats d'import (5.1) — ces trois-là
seront confirmés sur données réelles en 6.6, ce qui borne certaines décisions
ci-dessous (« revoir après 6.6 »).

Règle appliquée à chaque item — une notion entre dans le canon seulement si :

1. **≥ 3 plateformes** la portent nativement avec des *formes différentes*
   (c'est la normalisation qui justifie un champ canon ; une forme unique se
   contente de `sourceExtension`) ;
2. **au moins une cible** peut la consommer, OU un code de perte uniforme
   (`loss_<cible>_<notion>`) est plus honnête que N silences namespacés ;
3. l'ajout est **additif et optionnel** ; sortie par défaut inchangée à l'octet.

Statuts : **CANON** (proposition d'ajout, `[PROPOSITION]`, à valider avant
implémentation) · **DÉJÀ-CANON** (rien à ajouter, clarification seulement) ·
**EXT** (`sourceExtension` seulement, décision ferme pour cette phase) ·
**DIFFÉRÉ** (hors périmètre ou preuve insuffisante ; condition de reprise
explicite).

## A. Les 7 items originaux (5.1, `concept-map.v0.json#canonEvolutionOpen`)

### A1. Multilingue — **CANON** `[PROPOSITION P1]`

**Preuve** — 5.1 comptait 1/6 (PrestaShop). Depuis : Shopware (`translated.*`
+ `seoUrls[]` par langue), Scraper (`name_fr`/`name_en`, `description_*`),
Shopify (`translations` au schéma, non exploré faute de 2ᵉ locale) ; WooCommerce
seulement via plugins (WPML/Polylang), Wix via multilingual app. **3 sources
réelles, 3 formes différentes** (objet traduit par entité / colonnes
suffixées / entités SEO par langue) → cas typique de normalisation.

**Décision** — proposer sur `CanonProduct` :

```ts
translations?: Record<string /* BCP-47: 'en', 'nl-BE' */, {
  title?: string; bodyHtml?: string; seoTitle?: string; seoDescription?: string;
  slug?: string;                       // seoUrls par langue (Shopware), post_name traduit
  options?: { name?: string; values?: Record<string, string> }[]; // valeurs d'option traduites (rare, Shopware)
}>;
```

La **locale par défaut reste dans les champs plats** (`title`, `bodyHtml`…) —
aucun sérialiseur ne change. `translations` ne porte *que* les autres locales.
Aucune cible CSV ne consomme aujourd'hui → chaque cible déclare
`loss_<cible>_translations` (uniforme, au lieu de trois silences namespacés).
La dimension **par sales channel** de Shopware (`seoUrls[].salesChannelId`)
reste `sourceExtension.shopware` : c'est un concept Shopware, pas une langue.

### A2. `orderFinancialBreakdown` — **DIFFÉRÉ**

Les commandes ne font pas partie des trois jeux réels (produits uniquement).
Aucune donnée nouvelle. Reprise : une phase « commandes réelles » regroupant
A2 + A7 (`isGuest`) + `taxLines[]`/`shippingLines[]`/`refunds[]` du snapshot.

### A3. Catégories multi-rattachement — **DÉJÀ-CANON** (clarification)

`CanonProduct.categories: string[]` est commenté « hierarchy path, root →
leaf » mais **tous** les parsers émettent *un chemin complet par catégorie
rattachée* (`["Maison > Salon", "Promo"]`) — le multi-rattachement est porté
depuis la Phase 1. Shopify se projette naturellement : `collections[]` →
`categories[]` (plat, many-to-many), `productType` → `productType`.
**Action** : corriger le commentaire du type dans `@eloshon/catalog`
(doc-only). Item clos.

### A4. Typage des metafields — **CANON** `[PROPOSITION P2]`

**Preuve** — Shopify : `namespace` + `key` + `type` déclaré (`string`,
`boolean`, `list.*`, `json`…). Shopware : `customFields` typés par
`customFieldSets[]` (type déclaré à l'avance : text/number/date/select).
WooCommerce : `meta_data[]` non typé mais **namespacé par convention** (`_`
= interne, préfixe plugin). BigCommerce : `custom_fields` plats. → Le *type*
est natif sur 2/3 réels, le *namespace* sur 3/3 (formes différentes).
Le namespace est en outre la **donnée d'entrée de 6.5** (filtrage des
namespaces injectés par des apps : `mm-*`, `app--*`, `_*`…).

**Décision** — proposer sur `metafields[]` :

```ts
metafields: { key: string; value: string;
  namespace?: string;   // 'custom', 'global', 'mm-google-shopping', set Shopware, préfixe WC
  type?: string;        // vocabulaire SOURCE verbatim ('single_line_text_field', 'boolean', 'number'…)
}[];
```

`key` garde sa forme actuelle (byte-identique) ; `namespace`/`type` sont
absents pour les sources qui ne les ont pas. Consommateur réel : la cible
Shopify (l'import CSV reconnaît `product.metafields.<ns>.<key>` et le type
via la définition) ; 6.5 pour le scoring.

### A5. Identifiants séparés (GTIN/EAN/UPC/ISBN/MPN) — **CANON** `[PROPOSITION P3]`

**Preuve** — Shopware : `productNumber` (SKU) / `ean` / `manufacturerNumber`
(MPN) — 3 champs distincts. BigCommerce : `UPC/EAN`, `MPN`, `GTIN`, `BPN`.
PrestaShop : `reference`, `ean13`, `upc`, `isbn`, `mpn`. WooCommerce :
`global_unique_id` (un seul, non typé). Shopify : `barcode` (un seul) +
`harmonizedSystemCode`. Wix : partiel. → **4/7 plateformes** distinguent
plusieurs identifiants ; les cibles BC et PrestaShop les consomment en
colonnes séparées.

**Décision** — proposer sur `CanonVariant` :

```ts
identifiers?: { gtin?: string; ean?: string; upc?: string; isbn?: string; mpn?: string; hsCode?: string; originCountry?: string };
```

`barcode` reste « l'identifiant unique de la plateforme » (Shopify `barcode`,
WC `global_unique_id`) → byte-identique. Quand la source distingue,
`identifiers.*` porte la ventilation **et** `barcode` reçoit le premier
disponible dans l'ordre `gtin → ean → upc → isbn` (règle *données*, dans le
catalogue `fields.v1.json`, pas dans le code). `hsCode`/`originCountry`
(Shopify `inventoryItem`, Shopware `customs`… à confirmer 6.6) rangés ici car
ce sont des identifiants douaniers par variante, pas des attributs.

### A6. `taxIncluded` / taxe par pays — **EXT** (décision ferme)

`taxIncluded` est un **réglage boutique** sur les 3 plateformes réelles (WC
`woocommerce_prices_include_tax`, Shopify `taxesIncluded` du shop, Shopware
par sales channel) — jamais un attribut produit. Il n'a pas sa place sur
`CanonProduct` ; il en aura une sur une future enveloppe `CanonCatalog.settings`
si un adaptateur d'écriture en a besoin. Taxe par pays (`tax.rules[]`) : 1/3
natif → `sourceExtension.shopware.tax` (déjà fait en 5.x). Le canon garde
`taxable` + `taxClass` (nom de l'entité taxe réutilisable). Item clos.

### A7. `isGuest` sur `CanonOrder` — **DIFFÉRÉ** (avec A2)

Concept universel, coût nul, mais hors périmètre produit de la Phase 6.
Regroupé avec A2.

## C. Les 2 candidats Shopware

### C1. Prix par règle × palier de quantité — **DIFFÉRÉ → revoir après 6.6**

Paliers de quantité natifs : Shopware (`prices[]` × `quantityStart/End`),
BigCommerce (`bulk_pricing_rules`), PrestaShop (`specific_price.from_quantity`)
— potentiellement 3, mais **2 sur 3 sont justement les plateformes de 6.6**,
non encore observées. Les prix **par règle** (`ruleId` : groupe client, pays,
devise) sont propres à Shopware. Décision : `sourceExtension.shopware.prices`
(déjà fait) ; **ne pas** dessiner `priceTiers[]` sur une seule forme
observée. Reprise automatique en fin de 6.6 si BC et PrestaShop confirment.

### C2. `regulationPrice` (Omnibus) — **DIFFÉRÉ → revoir après 6.6**

Natif Shopware seulement ; PrestaShop 8 et WooCommerce le font par module,
Shopify détourne `compareAtPrice`. 1/3 → `sourceExtension.shopware`.
Reprise si PrestaShop 8/9 réel (6.6) expose un prix de référence légal
distinct du barré.

## D. Les 3 constats Shopify

### D1. Taxonomie fermée `category` — **EXT** (décision ferme)

Unique (`TaxonomyCategory`, arbre contrôlé par Shopify, sert Google/Meta
Shopping). Aucune des autres plateformes n'a de taxonomie **externe fermée**
sur l'entité produit (WC/BC : via plugins/feeds). Conservé
`sourceExtension.shopify.category` = `{ id, fullName }` — `fullName` est un
chemin lisible (« Home & Garden > … ») directement réutilisable par un flux
Google Shopping sur la cible. Pas de champ canon : ce n'est ni `categories`
(rattachement marchand) ni `productType` (texte libre).

### D2. Bundles / `requiresComponents` — **CANON, conçu en 6.4**

Deux plateformes indépendantes (Shopify `productComponents`, PrestaShop
`pack`) + Shopware `bundleComponents` au schéma. Décision de principe : entre
dans le canon (`kind: 'bundle'` + `components[]`). La forme exacte est l'objet
de **6.4** ; rien n'est ajouté ici.

### D3. Metafields à double surface — **DÉJÀ-CANON + règle parser**

Le SEO Shopify *est* stocké en metafields `global.title_tag` /
`global.description_tag` ; `product.seo` n'est qu'un alias. Aucun changement
canon (`seoTitle`/`seoDescription` existent). **Règle parser (6.3, donnée dans
`shopify.products.admin-graphql.v1.json`)** : `seo.*` → canon, et les
metafields `global.title_tag`/`description_tag` sont **consommés** (`consumes`)
pour ne pas apparaître deux fois. Les namespaces injectés par des apps
(`mm-google-shopping` observé) restent des metafields *portés* — jamais
supprimés (pas de perte) — mais **jamais proposés** comme candidats (6.5),
grâce à `namespace` (**P2**).

## E. Marqueur de provenance `inherited` — approuvé, implémenté en 6.2

`CanonProvenanceMethod` gagne `'inherited'` (valeur héritée du parent,
résolue par `structure.inheritance`). Remplace `method: 'structural' +
note: 'inherited from parent'`. Additif, type + parser générique ; goldens
canon (`shopware_api__*.canon.json`) changent **uniquement** sur ces deux
propriétés — à vérifier au diff.

d'écriture Shopware — reportée à l'ouverture d'une phase « write-adapter ».
