# Phase 6.5 — Metafields : les namespaces injectés par des apps ne sont jamais des candidats

Date : 2026-09-21. Règle (D3, 6.1) : un metafield écrit par une app tierce
est **porté** (jamais supprimé — aucune perte) mais **jamais proposé** comme
candidat de correspondance vers un champ canon. `mm-google-shopping` et
`app--<id>--*` sont des **instances** ; le mécanisme est un classifieur de
propriété de namespace, piloté par données, valable pour toute plateforme.
241/241 ; goldens byte-identiques.

## 1. Le mécanisme (`recognition.v1.json#metafieldOwnership`, `semantic.mjs`)

Une colonne est d'abord reconnue comme **metafield** par `columnPatterns`
(Shopify `<label> (product.metafields.<ns>.<key>)` ; WooCommerce
`Meta: <key>`) → `{ platform, namespace, key }`. Puis son **propriétaire** :

| Ordre | Signal | Données | Résultat |
|---|---|---|---|
| 1 | **Grammaire de réservation** de la plateforme elle-même | Shopify : namespace `^app--\d+--` (`$app:` résolu) ; WordPress : clé `^_` (`is_protected_meta`, cachée de la boîte « Champs personnalisés ») | `thirdParty` (via `grammar`) |
| 2 | **Listes** documentées, minuscules | `platformOwned.shopify = [global, shopify]` ; `merchantOwned.shopify = [custom, my_fields]` | `platform` / `merchant` (via `list`) |
| 3 | **Grappe de préfixes** dans **ce** fichier | ≥ `minKeys` (3) clés partageant un premier token « vendeur » — ni stop-token ni token du vocabulaire des champs (`name.stopTokens`, `tokenSynonyms`) : `rank_math_title / _description / _focus_keyword` → `rank` | `thirdParty` (via `cluster`) |
| 4 | **Défaut** | un **namespace** inconnu → `thirdParty` (`unknownNamespaceIsThirdParty`) ; une clé **sans** namespace (WooCommerce) → `merchant` | via `default` |

Pourquoi le défaut est conservateur : une app écrit toujours dans un
namespace qu'elle choisit ; le marchand crée les siens dans `custom` (défaut
de l'admin). Un namespace marchand hors liste (`specs`) est traité comme
tiers — le metafield est porté, seulement pas *proposé* ; une décision
(confirmer) ou la liste `merchantOwned` lève la restriction.

## 2. Dans le scoring (`recognizeColumns`)

- La colonne reçoit `context.metafield = { platform, namespace, key, owner,
  via }` (l'UI 6.7 l'affiche).
- Pour `owner === 'thirdParty'` : **tout candidat autre que `metafields`** est
  multiplié par `thirdPartyPenalty` (0) — **en dernier**, après tous les
  boosts (y compris « preuve par les valeurs seules ») pour que rien ne le
  ressuscite ; les candidats supprimés n'apparaissent pas (pas de
  « proposition pénalisée »).
- Le **port** `metafields` reste le seul candidat → statut `auto`. Pour cela,
  deux corrections de **données** dans `fields.v1.json` : la famille
  `metafields` reconnaît aussi la forme Shopify `(product.metafields.…)` en
  suffixe, et `metafields.accepts` couvre tous les profils (un metafield
  contient n'importe quel type — un profil EAN ne « contredit » pas le port).
- **Décisions Learned** : `confirmed` / `corrected` → `decided`, comme
  partout — l'utilisateur a le dernier mot ; le pont `analyzePlan` pré-remplit
  la règle correspondante (test).

## 3. Writer Learned (`learn.mjs`) et parser

- Une colonne metafield reconnue est écrite `metafield_pair` avec
  `args = { key: <clé source>, namespace: <ns> }` (P2) au lieu du libellé de
  colonne ; une colonne tierce porte une note (`carried as a metafield:
  namespace … is app-owned (default)`).
- `metafield_pair` accepte `args.namespace` → `metafields[].namespace`.
- Parser générique / `getPath` : une clé présente **verbatim** gagne sur la
  traversée pointée — une colonne CSV avec des points (`Prix H.T.`,
  `Condition (product.metafields.ns.key)`) était lue comme un chemin JSON et
  finissait « inconnue » (limite préexistante, corrigée ; `consumedKeys`
  compte aussi le chemin complet).

## 4. Preuves (`test/namespace-65.test.mjs`, 6 tests)

Classifieur pur (grammaire, listes, grappe, défaut, non-metafield → null,
`Meta:` espacé) ; Shopify : `google_product_category` / `condition` /
`app--777--gtin.barcode` → **seulement** `metafields`, la même colonne hors
namespace **serait** proposée (contrôle), `custom.ean` garde son candidat
identifiant ; WooCommerce : famille `rank_math_*` (grappe) et `_yoast_*`
(grammaire) portées, `Meta: ean` proposé ; décision confirmée → mappé malgré
le namespace tiers ; conversion Shopify → WooCommerce garde chaque colonne
metafield ; writer Learned + parser générique : clé + namespace portés.

## 5. Observation pour la suite

`[OBSERVATION]` Sur WooCommerce, le SEO *vit* dans des métas de plugin
(`rank_math_title`, `_yoast_wpseo_title`) : la règle les porte sans les
proposer comme `seoTitle`. C'est le comportement demandé ; le chemin de
sortie est la décision utilisateur (portée `family`/`global` possible) — une
liste « plugins SEO connus → seoTitle » serait précisément le genre de
liste que 6.5 évite. À revisiter si des utilisateurs le demandent.
