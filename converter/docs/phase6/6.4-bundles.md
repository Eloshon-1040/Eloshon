# Phase 6.4 — Bundles / packs : une représentation canon

Date : 2026-09-21. Décision de principe prise en 6.1 (D2 : « entre dans le
canon ») — cette phase est **conception + implémentation**, pas un nouveau
go/no-go. Additif ; 235/235 ; goldens antérieurs byte-identiques (seule
différence : les 24 clés brutes `components: []` des 3 snapshots 6.3
disparaissent — `copy_present`).

## 1. Les formes natives observées / documentées

| Plateforme | Niveau | Forme | Statut |
|---|---|---|---|
| **Shopify** | **variante** | `ProductVariant.requiresComponents` + `productVariantComponents.nodes[] = { id, quantity, productVariant { id, sku, product { id, handle } } }` — chaque variante du bundle liste SES variantes composantes (schéma vérifié via `graphql_schema`, aucun bundle sur la boutique de dev : `has_variant_with_components:true` → 0) ; `Product.hasVariantsThatRequiresComponents` ; `Product.bundleComponents` = la **configuration** du bundle fixe (produits + sélections d'options qui génèrent les variantes) | forme 1 |
| **PrestaShop 8/9** | **produit** | `product_type = 'pack'`, `associations.product_bundle[] = { id (produit), id_product_attribute (déclinaison ou 0), quantity }` ; un pack n'a pas de déclinaisons ; `pack_stock_type` (0 pack / 1 composants / 2 les deux) | forme 2 (à confirmer sur l'instance PS 9 locale en 6.6) |
| WooCommerce | — | `grouped` = produits liés achetés séparément (déjà `kind: 'grouped'`) ; pas de pack en standard | ≠ bundle |
| BigCommerce | — | « Product Pick List » = une **option** modificatrice où le client choisit un produit | ≠ bundle (option) |
| Wix, Shopware | — | rien en standard (Shopware : plugins tiers ; le `bundleComponents` évoqué en 6.1 n'est pas dans le schéma core) | EXT si rencontré |

Deux plateformes indépendantes, deux niveaux différents (variante / produit),
même concept : *vendu comme une unité, assemblé d'autres articles du
catalogue*. C'est la normalisation qui justifie le champ canon.

## 2. Forme canon (`@eloshon/catalog`)

```ts
CanonProductKind = … | 'bundle';
CanonBundleComponent = {
  ref: string;                                   // référence OPAQUE au composant, au niveau le plus précis connu (variante / déclinaison, sinon produit)
  refKind?: 'sku' | 'sourceId' | 'handle';
  quantity: number;                              // unités du composant par unité de bundle (≥ 1)
  productRef?: string; productRefKind?: …;       // le PRODUIT du composant quand ref est une variante
  title?: string;
};
CanonVariant.components?: CanonBundleComponent[];   // la composition, PAR VARIANTE
```

Pourquoi sur la variante : Shopify compose **chaque variante** du bundle
différemment ; un pack PrestaShop n'a qu'une variante (le pack n'a pas de
déclinaisons) → ses items vont sur cette variante unique. Une forme
produit aurait perdu la composition par variante Shopify. `kind: 'bundle'`
au niveau produit quand une variante a des composants (Shopify
`hasVariantsThatRequiresComponents`, PrestaShop `product_type = pack`).

`pack_stock_type` (PrestaShop) reste `sourceExtension.presta` : une seule
plateforme (Shopify décrémente implicitement les composants).

## 3. Un transform générique, deux formes par les args

`bundle_components` : `args.refs = [{ path, kind }, …]` essayés dans l'ordre
(les valeurs de `emptyValues` — `0` — comptent comme vides :
`id_product_attribute = 0` = « le produit lui-même »), `productRef`,
`quantity` (défaut 1), `title`.

- Shopify (`shopify.products.admin-graphql.v1.json`) : `refs`
  `[productVariant.sku → sku, productVariant.id → sourceId]`, `productRef`
  `productVariant.product.handle` ; `hasVariantsThatRequiresComponents`
  → `kind = bundle` (surcharge simple/variable) ; `bundleComponents.nodes`
  reste `sourceExtension.shopify` (configuration, spécifique).
- PrestaShop : `refs [id_product_attribute → sourceId, id → sourceId]`,
  `productRef id` — testé sur la forme Webservice documentée
  (`test/bundles-64.test.mjs`) ; l'entrée Reference PrestaShop complète
  arrive avec les données réelles de 6.6.

## 4. Cibles

Aucun import CSV produit (Shopify, WooCommerce, Wix, BigCommerce) ne crée une
composition : Shopify exige l'app Bundles / l'API, WooCommerce et BigCommerce
n'ont pas de packs en standard, Wix non plus. Le **produit bundle est repris
tel quel** (ses SKU / prix / stock — un `variable` WooCommerce pour un bundle
à variantes), la composition est déclarée : `loss_<cible>_bundles
{ count, handles }`, uniforme, localisé FR/EN. Les sérialiseurs ignorent
`components` (aucune fuite dans une cellule, test).

## 5. Couverture (`test/bundles-64.test.mjs`, 5 tests)

Bundle Shopify dans le shape exact de la réponse (Qnubu « duo », 2 variantes
composées de variantes réelles de la fixture) : kind, composants (sku +
handle), repli GID sans SKU, quantité par défaut, variante sans composant ;
pack PrestaShop par le même transform ; contrat du transform ; les quatre
cibles (export + perte uniforme + aucune fuite) ; boutique réelle : jamais
`bundle`, jamais de clé `components`.
