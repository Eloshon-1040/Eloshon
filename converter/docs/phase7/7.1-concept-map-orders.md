## `[OBSERVATION]` Constats structurants

1. **Numérotation** — six modèles, aucun import CSV de commandes nulle part :
   WooCommerce = id de post (trous normaux) ; Shopify = séquence `#1001`
   (préfixe/suffixe boutique, `name` jamais imposable) ; Shopware = plages de
   numéros par entité (`order {n}/10000`, `document_invoice {n}/1000` — la
   **séquence légale est celle du document**, pas de la commande ; l'API
   accepte un `orderNumber` explicite → collision à signaler) ; PrestaShop =
   **trois** identités (`id_order`, `reference` 9 caractères, `invoice_number`
   attribué par la machine d'états, préfixe `#IN`, `#DE` livraison) ;
   BigCommerce = l'id est le numéro (100, 101 observés, départ réglable en
   admin, non exposé) ; Wix = séquence depuis 10000, `imported: true`.
2. **Consentement** — 5/6 plateformes ont un champ ; **aucune** forme
   commune : Shopify `emailMarketingConsent { marketingState, marketingOptInLevel,
   consentUpdatedAt }` (+ SMS) ; Shopware = entité séparée `newsletter_recipient`
   (`status optIn|direct|optOut|notSet`, `confirmedAt`), le double opt-in du
   client étant celui du **compte** ; PrestaShop `newsletter` + `newsletter_date_add`
   (horodaté, observé) + `optin` (partenaires, autre consentement) ;
   BigCommerce : `accepts_product_review_abandoned_cart_emails` n'est PAS un
   consentement marketing, `/consent` = **cookies**, la newsletter = ressource
   `subscribers` ; Wix : `extendedFields['emailSubscriptions.subscriptionStatus']`
   (PENDING = double opt-in non confirmé) ; WooCommerce : rien en core.
   Les APIs d'import de Shopify (`emailMarketingConsent`), Shopware
   (`newsletter-recipient status optIn`) et Wix (`subscriptionStatus`) **permettent
   d'affirmer un consentement** — c'est exactement ce que 7.3 interdit.
3. **Taxes** — 5/6 portent un drapeau « prix TTC » au niveau commande
   (`prices_include_tax`, `taxesIncluded`, `taxStatus`,
   `is_tax_inclusive_pricing`, `taxIncludedInPrices`) que `CanonOrder` n'a pas.
4. **Payé vs dû** — PrestaShop `total_paid` vs `total_paid_real`, Wix
   `balanceSummary { paid, refunded, balance }`, BigCommerce `payment_status`
   + transactions : le canon n'a que `total`.
5. **Snapshot** — Shopware `orderCustomer`, BigCommerce/PrestaShop adresses
   copiées, lignes avec nom/prix/identifiants figés : une commande ne se
   re-dérive jamais du client courant.

## `[NÉCESSITÉ TECHNIQUE]` Constats « règle dure » (surfacés)

- **BigCommerce** `v3 /orders/{id}/transactions.credit_card { card_iin,
  card_last4, card_expiry_* }` + `cvv_result` + `avs_result` +
  `payment_instrument_token` — **observés avec valeurs** sur la transaction
  de test : PAN tronqué. Jamais capturés ; le scanner 7.7 les reconnaît par
  forme.
- **PrestaShop** `order_payments.card_number / card_brand / card_expiration /
  card_holder` (colonnes réelles, 0 ligne en démo) ; `customers.passwd`,
  `secure_key`, `reset_password_token`, `orders.secure_key` : supprimés à la
  capture.
- **Shopify** `CardPaymentDetails` (numéro masqué, BIN, expiration) : jamais
  sélectionné ; **Wix** `creditCardDetails.lastFourDigits` : idem.
- Aucune plateforme n'accepte un numéro de séquence imposé par son import
  CSV ; deux APIs l'acceptent (Shopware `orderNumber`, PrestaShop
  `reference`/`id`) → 7.4 les signale, ne les utilise jamais.
