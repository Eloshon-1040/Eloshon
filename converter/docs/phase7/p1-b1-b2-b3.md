## 5. `[PROPOSITION]` extensions canon génériques (non implémentées)

### 5.1 Qualificateur temporel sur la provenance (B1)
Vérification faite : rien dans le canon n'exprime la certitude d'un
horodatage (`CanonProvenance` = plateforme / champ / valeur / transform /
method / confidence réservé / note libre ; `CanonMarketingConsent.level` =
niveau d'opt-in, pas de temps). Une note en prose est exclue (jamais de prose).
Proposition additive, **une** propriété optionnelle sur `CanonProvenance`,
valable pour **tout** chemin canon daté (consentement `at`, `timestamps.*`,
`numbering.sourceInvoiceDate`, `payments[].at`…), tous connecteurs :
```ts
export type CanonProvenance = { …; temporal?: 'utc' | 'offset' | 'timezone_unknown' };
```
Posée automatiquement par le parser générique pour toute valeur produite par
un transform de date (`hasZone` : Z → `utc`, ±hh:mm → `offset`, sinon
`timezone_unknown`), y compris via `object_map as: 'date'`. Aucun champ métier
nouveau ; `consentReport.withTimestamp` pourrait alors distinguer horodaté-avec-
fuseau et horodaté-sans-fuseau **sans** nouveau champ de rapport.

### 5.2 Consentements à finalité (B3)
Vérification faite : `marketingConsent` est clé par canal (`email | sms`) ;
une finalité (« offres partenaires », « à la commande ») n'est pas
représentable sans clé nouvelle. Proposition additive :
```ts
export type CanonConsentPurpose = 'email_marketing' | 'sms_marketing' | 'partner_marketing' | (string & {});
export type CanonConsent = CanonMarketingConsent & { purpose: CanonConsentPurpose; collectedAt?: 'account' | 'checkout' | 'newsletter' | 'unknown' };
export type CanonCustomer = { …; consents?: CanonConsent[] };
```
- `purpose` = vocabulaire ouvert documenté (une nouvelle finalité = une valeur,
  pas un changement canon) ; `channel` reste (un `partner_marketing` peut être
  e-mail).
- Les quatre choses distinctes de B3 sont alors : **déclaration** =
  `source.raw` (+ `source.field/platform`), **statut** = `state`, **horodatage**
  = `at` (+ provenance `temporal`), **niveau de preuve** = `level` (opt-in) +
  `collectedAt` (où la déclaration a été faite) — sans champ `evidenceLevel`.
- `marketingConsent.email / sms` restent la vue de compatibilité (dérivée de
  `consents[]` à finalité `email_marketing` / `sms_marketing`).
- Consommateurs : PrestaShop `optin` → `{ purpose: 'partner_marketing',
  state: 'pending' (pas d'horodatage), source.raw '1' }` ; BigCommerce
  `is_email_opt_in` → `{ purpose: 'email_marketing', collectedAt: 'checkout',
  state: 'pending' }` **si** la décision B3(i) le classe comme déclaration ;
  Shopify `emailMarketingConsent` (données réelles capturées) → `opted_in`
  avec `consentUpdatedAt` + `level` ; Wix / Shopware inchangés.
