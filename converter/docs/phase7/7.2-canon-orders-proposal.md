# Phase 7.2 / 7.3 / 7.4 — `[PROPOSITION]` Types canon commandes, clients, paiements, consentement, numérotation

Date : 2026-09-21. **Non implémenté** — soumis avant toute modification de
`@eloshon/catalog`. Fondé sur `concept-map-orders.v0.json` (7.1).

Principes :
1. **Nouveaux types séparés**, jamais greffés sur `CanonProduct`. Les
   `CanonCustomer` / `CanonOrder` / `CanonLineItem` actuels restent
   **byte-identiques** (les parsers/sérialiseurs CSV clients/commandes de
   Phase 1–4 en dépendent) : les nouveaux types sont `CanonOrderV2`,
   `CanonCustomerV2`… **ou** — proposition retenue ci-dessous — les types
   actuels reçoivent uniquement des champs **optionnels additifs** et deux
   types neufs (`CanonOrderLineItem`, `CanonPayment`) coexistent avec
   `CanonLineItem`. À trancher (question 1).
2. **Données archivistiques** : une commande est immuable ; ce qu'elle porte
   est un **snapshot** (adresses, lignes, identifiants au moment de la
   vente), jamais re-dérivé du catalogue ou du client courant.
3. **Faits financiers agrégés seulement** : `CanonPayment` ne porte ni jeton
   de passerelle, ni donnée de carte (7.7 les retire avant canonicalisation).
4. **Le consentement ne se copie pas** : il se rapporte, avec sa preuve.

Invariant (test 7.7) : aucune valeur de `CanonPayment` (ni de tout objet
canon) ne satisfait la forme PAN (13–19 chiffres Luhn), CVV adjacent à un
champ carte, IIN+last4, expiration MM/YY liée à une carte, IBAN complet.

## 4. `CanonCustomer` (additif) et 7.3 consentement

```ts
export type CanonMarketingConsent = {
  state: 'opted_in' | 'opted_out' | 'pending' | 'unknown';   // défaut : 'unknown'
  level?: 'single_opt_in' | 'confirmed_opt_in' | 'unknown';    // double opt-in confirmé ou non
  at?: string;                       // horodatage DE LA SOURCE (consentUpdatedAt, newsletter_date_add, confirmedAt, subscribers.date_created) — obligatoire pour 'opted_in'
  channel: 'email' | 'sms';
  source: { platform: string; field: string; raw?: unknown };  // preuve : d'où vient l'affirmation
  requiresReconfirmation: true;      // TOUJOURS true : un consentement source n'est pas un consentement cible
};
export type CanonCustomer = {
  // ── existants (inchangés) ──
  firstName: string; lastName: string; email: string; phone: string;
  address: CanonAddress; shipping: CanonAddress | null;
  acceptsEmail: boolean | null; acceptsSms: boolean | null;   // ⚠ sérialisés désormais comme "non abonné" par défaut (voir § 6)
  note: string; tags: string[]; taxExempt: boolean;
  // ── 7.2 additifs ──
  identity?: { sourceId?: string; customerNumber?: string; username?: string; timestamps?: { created?: string; modified?: string; lastLogin?: string } };
  isGuest?: boolean; active?: boolean; state?: string;           // Shopify state, PS active, SW active
  company?: { name?: string; vatIds?: string[]; registrationIds?: string[] };   // siret/ape, vatIds[]
  group?: { ref?: string; name?: string };
  locale?: string; birthday?: string; gender?: string;
  addresses?: (CanonAddress & { label?: string; kind?: 'billing' | 'shipping' | 'both'; isDefaultBilling?: boolean; isDefaultShipping?: boolean; vatNumber?: string; sourceId?: string })[];
  // ── 7.3 ──
  marketingConsent?: { email?: CanonMarketingConsent; sms?: CanonMarketingConsent };
  stats?: { orderCount?: number; totalSpent?: number | null; currency?: string; lastOrderAt?: string };  // faits, jamais recalculés
  sourceExtension?: CanonSourceExtension; unmapped?: UnmappedEntry[]; provenance?: CanonProvenanceMap;
};
```

Règles 7.3 (parser générique, données) :
- `state: 'opted_in'` **seulement si** la source l'affirme explicitement
  **et** fournit `at` ; sans horodatage → `'pending'` avec `source.raw`
  (PS `optin=1` sans date, BC `subscribers` sans date). Shopify `PENDING`,
  Wix `PENDING`, SW `notSet` → `'pending'`. `UNSUBSCRIBED`/`optOut`/`0` → `'opted_out'`.
  Tout le reste → `'unknown'`.
- BC `accepts_product_review_abandoned_cart_emails` et `/consent`
  (cookies) ne sont **pas** des consentements marketing → `sourceExtension`.
- PS `optin` (offres partenaires) est un consentement **distinct** →
  `sourceExtension.presta.optin` + rapport.
- Cibles : la colonne / le champ d'abonnement de la cible est émis à
  **non abonné** (`Accepts Email Marketing = no`, `newsletter = 0`,
  `emailMarketingConsent` omis, Wix `subscriptionStatus` non affirmé),
  quoi que dise la source. Perte déclarée : `loss_<cible>_marketing_consent
  { customers, explicit, pending }`.

Rapport marchand (7.3, `ConvertResult.consentReport`) :
```
{ customers: N, explicitSourceConsent: M, withTimestamp: M', pending: P, optedOut: O, unknown: U,
  message: "N clients migrés — M avaient un consentement explicite sur <source> (M' horodatés) :
            ils sont importés NON abonnés ; recueillez votre propre confirmation (double opt-in) avant tout envoi." }
```

## 5. 7.4 — Intégrité de numérotation

- `numbering.sourceNumber` immuable ; la cible génère sa séquence
  nativement : **aucun** sérialiseur/adaptateur n'écrit `orderNumber`
  (Shopware), `reference`/`id` (PrestaShop), `name` (Shopify) — même quand
  l'API l'accepte.
- Le numéro source est porté **visiblement** sur la cible : note /
  `staff_notes` / tag / `external_id` (BC) / `sourceIdentifier` (Shopify)
  / metafield `migration.source_order_number` — au choix du format cible
  (données), jamais dans la séquence.
- Rapport `ConvertResult.numberingReport` : `{ orders, sourceSequence:
  { min, max, gaps: [ranges], duplicates: [numbers] }, invoices: { withNumber,
  withoutNumber, gaps }, targetPolicy: 'native-sequence', warnings }` —
  trous et doublons **source** rapportés (une facture manquante dans la
  séquence légale source est un fait à signaler, pas à corriger).
- Conflit : si deux sources migrent vers une cible avec des `sourceNumber`
  identiques → `warning numbering_source_duplicate`, jamais fusionné.

## 6. Compatibilité et pertes

- Types existants : aucun champ requis ajouté ; les parsers/sérialiseurs
  CSV actuels (Shopify / WooCommerce / BigCommerce clients & commandes)
  restent byte-identiques **sauf** un point à trancher : `acceptsEmail`
  aujourd'hui recopié tel quel vers `Accepts Email Marketing` (Shopify) /
  `Receive Marketing Emails` (BC). 7.3 impose **non abonné** par défaut →
  **changement de goldens intentionnel** (`shopify_customers__*`,
  `bigcommerce_customers__*`, `woo_customers__to_shopify`) + perte
  `loss_<cible>_marketing_consent`. (question 2)
- Codes de perte uniformes : `loss_<cible>_order_numbering` (le numéro
  source ne devient pas le numéro cible — informatif, toujours présent quand
  des commandes sont converties), `loss_<cible>_invoice_numbers`,
  `loss_<cible>_payments_detail`, `loss_<cible>_marketing_consent`.
