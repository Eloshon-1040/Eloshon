# Phase 7.2 / 7.3 / 7.4 / 7.6 — Commandes, clients, paiements, consentement, numérotation : implémentation

Date : 2026-09-21. Implémente la `[PROPOSITION]` 7.2 telle que validée
(`[DÉCISION UTILISATEUR]` : 1 additif sur les types existants ; 2 non-abonné
par défaut aussi sur les chemins CSV ; 3 marque de carte conservée ; 4
commandes de test exclues) plus la création de commandes de test locales
(Shopware / PrestaShop) pour observer la numérotation légale **en action**.

## 1. Types canon (`@eloshon/catalog` daebd47)

Additif sur `CanonCustomer` / `CanonOrder` (tout champ pré-Phase-7
byte-identique), deux types neufs (`CanonOrderLineItem`, `CanonPayment`), plus
`CanonMarketingConsent` (`requiresReconfirmation: true` **toujours**),
`CanonCustomerAddress`, `CanonOrderNumbering`, `CanonOrderStatus`. Le
converter ré-exporte tout (`core/src/types.ts`) et `ConvertResult` gagne deux
rapports optionnels : `consentReport` (clients) et `numberingReport`
(commandes).

## 2. Moteur

### Parser générique — mode entité (`generic-parser.mjs`)
`format.entity: 'orders' | 'customers'` route vers `parseEntities()` : les
entrées de scope `item` (ou canon `items[].…`) s'appliquent à chaque ligne
(`structure.items` : tableau inline ou companion clé par l'id de commande),
les autres à l'unité. Mêmes garanties que les produits (consommé / préservé /
listé, provenance) ; `lineItems[]` (vue simple pré-Phase-7) est **dérivée**
de `items[]` ; les champs plats hérités (`number`, `total`,
`financialStatus`, `paymentMethod`, `transactionId`…) sont remplis par des
**dérivations canon** de scope `order` / `customer`
(`canon/fields.v1.json#derivations`, 14 règles ajoutées) — jamais par du code
plateforme.

### Transforms (données, pas de code par plateforme)
`object_map` / `objects_map` (construction d'objets canon depuis un mapping
`{ canonKey: path | { path, as, map, value, join, paths, ref, require,
skipZero } }`), `lookup` (jointure sur un companion : PrestaShop
`order_states`, `addresses`, `countries`…), `address_from` (+ `lookup`, `each`,
`select.whereFrom`, `refs`), `marketing_consent` (règle 7.3, + `lookup` vers
`newsletterRecipients` / `subscribers`), `format_number` (`#IN000001`),
`split_name_options` (PrestaShop replie la déclinaison dans le nom de ligne),
`sum_of`, `subtract`, `id_or_none`, `is_unset`, `date_present`,
`money_present`, `money_nonzero`, `text_present`, `first_number`.

## 3. Règles dures — comment elles sont tenues

### 7.7 Cartes (déjà en place, vérifié en sortie)
Scanner à l'ingestion (JSON et CSV) **avant** toute entrée. Test 7.6 : aucun
objet canon ni aucune ligne cible des 14 cas ne contient de donnée de carte,
jeton, IBAN ou identifiant (`scanForCardData` sur les sorties). La marque
(`instrument.brand: 'master'`) et la référence de passerelle (`providerRef`)
restent — ce sont des faits de paiement (décision 3).

### 7.4 Numérotation
- `numbering.sourceNumber` immuable ; **aucun** sérialiseur n'écrit la
  séquence cible. WooCommerce : `ORDERID` **vide** (un importateur qui
  reçoit une valeur met à jour / réclame cet ID — c'est exactement le risque
  visé) + colonne `meta:_source_order_number` ; le plan de mapping promet
  désormais cette colonne. Shopify : `Name` reste la **clé de regroupement
  des lignes** (`name` est en lecture seule côté Shopify : la séquence est
  native quoi qu'il arrive) — documenté dans la perte.
- `numberingReport { orders, sourceSequence { min, max, numeric, gaps,
  duplicates }, invoices { withNumber, withoutNumber, gaps }, targetPolicy:
  'native-sequence', warnings }` ; avertissements `numbering_source_duplicate`
  (jamais fusionné) et `numbering_source_gaps` (un fait, pas une correction) ;
  pertes uniformes `loss_<cible>_order_numbering`, `loss_<cible>_invoice_numbers`,
  `loss_<cible>_payments_detail`.
- Les chemins CSV existants reçoivent le même rapport (le numéro plat **est**
  le numéro source).

`[OBSERVATION]` Numérotation légale observée **en action** :
- **Shopware** (deux checkouts Store API réels, `shopware-seed-orders.mjs`) :
  `orderNumber` 10000 puis 10001 (plage `order`, start 10000, `lastValue`
  avancé), transactions passées `paid` par l'Admin API, documents facture
  `documentNumber` 1000 puis 1001 (plage `document_invoice`) attribués à la
  **création du document**, pas à la commande. Prix facturé 800 = palier
  quantité (preuve C1 supplémentaire).
- **PrestaShop** (orders 2 et 4 passées « Payment accepted » = état
  `invoice 1`, `paid 1`) : `invoice_number` 1 puis 2 attribués dans l'**ordre
  des changements d'état** (pas l'ordre des commandes), `invoice_date`
  posée, `valid 1`, `total_paid_real` renseigné, lignes `order_invoices`
  et `order_payments` (par `order_reference`, `card_*` retirés à la capture).
  Les trois commandes non payées gardent `invoice_number 0` → aucun numéro
  canon. Préfixe `#IN` = `PS_INVOICE_PREFIX` par défaut, affiché sur 6
  chiffres — porté comme `numbering.format` pour le rapport seulement.

### 7.3 Consentement
- `marketing_consent` : `opted_in` **seulement** si affirmation explicite
  **et** horodatage source (`newsletter_date_add`, `confirmedAt`,
  `subscribers.date_created`) ; affirmation sans horodatage → `pending`
  (colonnes CSV Shopify / BigCommerce « yes », Wix `SUBSCRIBED`, Shopware
  `direct` sans `confirmedAt`) ; `optOut` / `0` / `UNSUBSCRIBED` →
  `opted_out` ; le reste → `unknown` ; rien d'affirmé → pas de bloc.
- **Toutes** les cibles écrivent non abonné : Shopify `Accepts Email
  Marketing = no` et `Accepts SMS Marketing = no`, BigCommerce `Receive
  Marketing Emails = N`, WooCommerce (pas de colonne). Y compris les chemins
  CSV existants (décision 2) → goldens clients modifiés **intentionnellement**
  (`shopify_customers__to_woo`, `woo_customers__to_shopify`,
  `bigcommerce_customers__*`) ; l'ancienne perte `loss_marketing_consent`
  (« inconnu ») est remplacée par `loss_<cible>_marketing_consent
  { customers, explicit, timestamped, pending }` ; `consentReport` typé.
- Les parsers CSV clients produisent aussi la preuve (`consentEvidence`) :
  une colonne oui/non = affirmation sans horodatage.
- PrestaShop `optin` (offres partenaires) reste un consentement distinct,
  préservé et listé (`unmapped`, `no-canon-field`), jamais fusionné.
