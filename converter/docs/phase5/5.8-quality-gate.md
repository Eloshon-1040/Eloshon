## Round-trip (`test/roundtrip.test.mjs`)

WC REST → canon → **CSV WooCommerce** → parser CSV → canon′ : égalité stricte
sur les champs étendus que le CSV WC sait porter. Pour cela, sérialiseur et
parser CSV WC ont été enrichis **additivement** avec les colonnes réelles de
l'exporteur WooCommerce — `Is featured?`, `Date sale price starts/ends`,
`Backorders allowed?`, `Sold individually?`, `Tax class`, `Shipping class`,
`Purchase note`, `Position`, `Upsells`, `Cross-sells`, `External URL`,
`Button text`, `Download N name/URL`, `Download limit/expiry`, attributs
descriptifs (`Attribute N …`, `visible`). Une colonne n'est émise que si un
produit porte le champ ⇒ sortie par défaut byte-identique.

Un produit synthétique couvre les champs absents des données live (période de
promo, téléchargements, externe, note d'achat, classes, upsells résolus vers
les SKU du lot).

## Contrat analyse ↔ conversion (`test/parity-contract.test.mjs`)

Automatisé sur toute la matrice :
- (A) tout binding **appliqué et repris** par la cible existe dans la sortie
  et y porte une valeur dès que la source en a ;
- (B) pour un format piloté par la connaissance, tout champ déclaré non vide à
  la source est livré dans le canon (provenance) et toute clé source est
  consommée ou conservée + listée ;
- (C) le sémantique ne contredit jamais une règle exacte.

Le contrat a trouvé une vraie incohérence : la cible BigCommerce promettait
`categories → "Categories (IDs conservés)"` alors que le sérialiseur n'écrit
aucune colonne catégorie (`loss_bc_categories_target`). Corrigé dans les
données (`TARGET_FIELDS`), sans effet sur la sortie.
